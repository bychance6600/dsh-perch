# 调研：AI 养成/伴侣类项目，以及「养过的人能不能迁进来」

> 2026-11-10。范围：DSH 插件市场（[awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin) 全量 9714 条）按关键词筛过一遍，另在 GitHub 上按中文与英文关键词找 12 个代表性开源项目，逐个读 README / 源码。
>
> star 与最近更新为 GitHub API 实测（2026-11-10）。抓不到的写「没查到」，不做推测。本文只陈述别人怎么做。

## 一、结论先行

1. **人格基本是配置出来的。** 市场 421 条人格/伴侣相关条目里，明说角色卡的 31 条、明说成长或好感的 29 条、两者同时出现的 1 条；逐个读过 README 的 18 个 DSH 项目里 12 个的人格来自角色卡、系统提示词或设置页字段，2 个靠数值（galgame 好感度、zhu-pet 亲密度），2 个声称从事件里长出来（[dsh-fish](https://github.com/ssamurias/dsh-fish)、[lingshu-skill](https://github.com/Q2667671398/lingshu-skill)），1 个（[digipet](https://github.com/swaylq/dsh-digipet)）根本没有 persona，1 个没查清。
2. **记忆主流是「向量库 + 摘要」，导出主流是 SillyTavern 的 .jsonl。** 角色卡生态（SillyTavern 及一整排 DSH 酒馆插件）把「卡 PNG/JSON + 世界书 + 聊天 .jsonl」做成了事实标准；自建项目多走 mem0/Qdrant/pgvector 加每日摘要，导出能力参差。
3. **迁移时能拿到的是文本，不是状态。** 大多数项目能导出对话原文和一张角色卡；好感度、亲密度、进化分支、阶段、向量库里的记忆条目，基本没有对应的导出物。这与「迁经历可以、迁人设不行」正好对上：卡是配置，聊天记录才是经历。

## 二、口径与方法

- **市场侧**：`awesome-dsh-plugin` 的 README 3,421,298 字节、9714 条条目；插件 yml 只有 `url / name / category / description{en,zh}` 四个字段，`category` 例：`ui / fun / memory / remote`。**形态与人格来源都不在元数据里，只能读 description 与 README。**
- **关键词**：`persona|character card|角色卡|人设|waifu|companion|伴侣|人格` 命中 421 条；在此集合内叠加 `character card|角色卡|persona card|人设卡|sillytavern` 剩 31 条（全站共 36 条），叠加 `grow|growth|evolv|raise|养成|成长|affection|好感` 剩 29 条，两者交集 1 条。
- **低估风险**：只按描述文字统计。一个插件可能支持角色卡但描述里没写，这类不会进 31；所以 31 是下界，不是全貌。
- **GitHub 侧**：中文搜 `AI 伴侣 / 养成 / 虚拟女友 / 角色卡`，英文搜 `AI companion memory / persona card / SillyTavern`。未认证 API 限额 60 次/小时、搜索 10 次/分钟，因此只为挑出来的项目逐个查了 star 与 `pushed_at`。
- **「形态」的三类**：工作区会话（插件挂在 DSH 里，人格与记忆落在某个工作区）/ 独立 App 或 Electron / 纯前端（浏览器里跑，卡与聊天都存在本地目录）。

## 四、角色卡：人格在文件里长什么样

这一节是后面三个问题的基础。角色卡格式由社区规范定义，[character-card-spec-v2](https://github.com/malfoyslastname/character-card-spec-v2) 给出 V1/V2 的 TypeScript 定义：

```ts
type TavernCardV1 = {
  name: string; description: string; personality: string
  scenario: string; first_mes: string; mes_example: string
}
type TavernCardV2 = {
  spec: 'chara_card_v2'; spec_version: '2.0'
  data: TavernCardV1 & {
    creator_notes: string; system_prompt: string
    post_history_instructions: string
    alternate_greetings: Array<string>
    character_book?: CharacterBook
    tags: Array<string>; creator: string
    character_version: string; extensions: Record<string, any>
  }
}
```

**V1 的「人格」就是六个字符串字段，其中有一个字段字面就叫 `personality`。** V2 增加 `system_prompt`、越狱用的 `post_history_instructions`、备选开场白与内嵌世界书（`character_book`）；V3（`chara_card_v3`）被 [dsh-tavern-v2](https://github.com/chen731215-dev/dsh-tavern-v2) 使用，字段是 V2 的超集。
落盘有两种：JSON 文件，或把同一段 JSON 做 base64 塞进 PNG 的 `tEXt` 块。SillyTavern 的 [character-card-parser.js](https://github.com/SillyTavern/SillyTavern/blob/release/src/character-card-parser.js) 同时认 `chara`（V2）与 `ccv3`（V3），注释写「V3 (ccv3) takes precedence」，解码就是 `Buffer.from(textChunks[i].text, 'base64').toString('utf8')`（L57–L67）。
所以「迁人设」在文件层面就是搬一段文本；反过来，「卡里没有的东西」也就永远不在卡里——比如她经历过什么。

## 六、三个问题

### a. 人格是配置出来的还是长出来的

| 口径 | 配置（卡 / 提示词 / 字段） | 数值或分支 | 事件长出 | 无 persona / 不适用 |
| --- | --- | --- | --- | --- |
| DSH 市场 421 条条目 | 明说角色卡 31 条（7.4%） | 明说成长/好感 29 条（6.9%，含数值与阶段解锁） | 未单列（只有 dsh-fish 明说） | 其余大量纯桌宠 |
| 读过的 18 个 DSH 项目 | 12 个 | 2 个（galgame、zhu-pet） | 2 个（dsh-fish、lingshu-skill 自称） | digipet 无 persona，另 1 个没查清 |
| 非 DSH 12 个项目 | 9 个 | 0 个 | 0 个 | 3 个（AIRI、Open-LLM-VTuber 无成长；清单/记忆基础设施不适用） |

配置派的做法高度同构：一张卡 + 一段世界书 + 一段 system prompt，换卡即换人。[dsh-cosplay](https://github.com/liceses/dsh-cosplay) 甚至提供「规则卡在模型看到前改写用户消息」这种把人格做成输入过滤器的写法；[assistant-profile](https://github.com/iStarryDust/dsh-assistant-profile) 把 persona 做成每个新会话都携带的全局字段。
长出派只有 dsh-fish 把机制写清楚了：四阶段、三道瓶颈（自主/主动各一次）、记忆有重量、事件流是唯一可信源。lingshu-skill 只自称「persona and growth system」，README 没给出阶段与证据规则（没查到细节）。
数值派介于两者之间：galgame 的 affection 靠日常互动与工作 token 累积、zhu-pet 的亲密度靠喂、digipet 沿四条分支进化——关系有「成长」，但成长是标量或分支，不是判断。agentic-pet 是混合体：人设是设置页字段，关系仍记在好感账本上。

### b. 记忆怎么存，能不能导出

| 存法 | 代表 | 检索 / 维护 | 导出物 |
| --- | --- | --- | --- |
| 聊天 `.jsonl` 文件 | SillyTavern | 前端按角色分目录，分支另存 | `.jsonl`，源码里就是 `chatData.map(m => JSON.stringify(m)).join('\n')`（[chats.js](https://github.com/SillyTavern/SillyTavern/blob/release/src/endpoints/chats.js) L533） |
| 向量库 | Artemis(mem0+Qdrant)、AionsHome、companion-app(Pinecone/pgvector) | embedding + 相似度；Artemis 加 BM25 混合、每角色独立 `user_id` | 一般要调 API/写脚本；AionsHome 有文件导出入口 |
| 摘要 | tavern-v2（memory summaries）、NextTavern（后台导演笔记）、AionsHome（1 小时无消息自动总结） | 定时或空闲触发，摘要回注上下文 | 摘要本身是文本，但常与原文分开存放 |
| 全文 / 固定注入 | NextTavern「固定设定不压缩始终注入」 | 上下文硬切窗口 + 尾部保留 | 卡与小说可导出，聊天原文未见导出（没查到） |
| 本地目录文件 | dsh-fish(`events.jsonl`)、OpenAmika(`memory_f`、`brain\memories`)、mem0 的 markdown dump | 直接读写文件 | 目录本身就是导出物 |
| 无 | airi（Memory 未完成）、dsh-cosplay、digipet | — | 无 |

NextTavern 的记忆写得最细，[README 第 147 行](https://github.com/a86582751/dsh-nexttavern)把它拆成四件：固定设定不压缩始终注入 + 有尾部保留的上下文硬切窗口 + 可追溯来源的后台导演笔记 + 关键词和语义混合查询召回。
能导出对话记录是少数：SillyTavern 系（.jsonl）、tavern-v2（文件夹 + manifest）、Artemis（可反向导入 ST JSONL）、AionsHome（文件管理）、OpenAmika（目录）。NextTavern 只承诺导出角色卡与小说稿，README 明确「旧会话不兼容，小说稿不保存完整会话状态」。数值型项目（galgame / digipet / zhu-pet）只存进度，没有可读的经历文本。

### c. 迁到 dsh-roost，技术上最可能拿到什么

| 来源 | 能拿到 | 拿不到 |
| --- | --- | --- |
| SillyTavern / 酒馆系 | 对话 `.jsonl` 原文、角色卡 PNG/JSON、世界书 | 无派生状态（本来就没有） |
| Artemis | ST JSONL 可导入其 `memory/role_play/<character>/`，等于原文可编程落盘；卡可解析 | mem0 里的摘要与向量（要另跑 Qdrant 导出） |
| tavern-v2 | 角色卡（双格式）、世界书、预设、manifest | 聊天记录导出没查到 |
| NextTavern | 角色卡、小说稿 | 旧会话、完整会话状态 |
| dsh-fish | 人设正文 1200–1500 字、称呼、工具白名单；事件流里留 `import-mark:` | 好感度数值、原事件流（导入即重开） |
| galgame / agentic-pet / digipet / zhu-pet | 几乎没有文本；最多一张设定说明 | 好感度、亲密度、进化分支、阶段 |
| airi / Open-LLM-VTuber | 角色配置文本 | 记忆（本来就没有或不完整） |
| mem0 / letta 用户 | 可用 SDK/API 全量导出记忆条目 | 没有标准格式，需自己写映射 |

一句话：**最可能拿到的是「聊天原文 + 一张卡」，最不可能拿到的是「长出来的状态」。** 前者正好是事件流能吃的原料，后者在任何项目里都没有可移植的表示。

## 七、上游样本：dsh-fish 的导入

[dsh-fish](https://github.com/ssamurias/dsh-fish) 是本项目的上游（dsh-roost 由它演进而来），它的 README 写得很直白：默认从空白开始养，但「可导入你已经养过的大肥鱼人设提示词」。导入只带三样——人设正文（1200–1500 字，超 2000 字拒收）、怎么称呼你、工具白名单；好感度数值不进来，「进入本插件环境后她看不到自己的好感度」；导入这件事本身靠事件流里的 `import-mark:` 留痕。
它把「迁人设」做成了「迁一段文本 + 重新开始计数」，而不是搬运状态。官方市场条目（[README](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin) 第 3614 行，维护者 fkysly 在合并后的 `1cb18d6` 里补写）也写明「Evolved from ssamurias/dsh-fish，注册同名工具，不能同装」。

## 八、对 dsh-roost 的启示

**值得抄（3 条）**

1. **先会读 ST 的 `.jsonl`。** 它是这个生态里唯一的事实标准，且已有可编程解析的先例（Artemis 直接读 ST JSONL 建记忆目录；SillyTavern 自己一行 `join('\n')` 写盘）。「要不要开导入入口」是产品决定，不在本文范围；这里只记格式与先例——真要接别人的经历，这是唯一不用猜的文本层。
2. **记忆条目带来源指针。** NextTavern 的「可追溯来源的后台导演笔记」是少数把「这条记忆从哪句话来」写进设计的项目；我们的事件流天然有 id，值得在导入时保留 `source: <proj>:<msg_id>`。
3. **导出清单照 tavern-v2 做。** 一个文件夹 + 双格式卡 + `manifest.json` + 说明.txt，是用户能自己拿走、别人能自己解析的最小公约数。若我们提供导出，照这个形状即可。

**明确不要（3 条）**

1. **好感度/亲密度数值**（galgame、agentic-pet、zhu-pet、digipet 都用数值或分支驱动关系）。数值可以刷、可以喂、可以改，和「按证据推进」互斥。
2. **角色卡注入 system prompt**（cosplay、persona-shaoxin、assistant-profile、bard）。人格一旦是每轮都注入的文本，就永远停在配置层。
3. **「拖卡即换人」**（Artemis 导入卡时切换 persona）。把人格当皮肤换，等于承认人格是可替换的外壳。

**迁移难度：中等。** 分档看：

- 酒馆系（ST / tavern-v2 / Artemis / NextTavern）→ **容易**：有 `.jsonl` 或卡，文本层完整，写个导入器即可；
- 自建向量库（AionsHome / OpenAmika / mem0 用户）→ **中等**：原文要写脚本捞，摘要和向量得重算；
- 数值型桌宠（galgame / digipet / zhu-pet）→ **很难**：只有进度没有经历，迁过来等于从零养；
- 闭源 App（星野 / 猫箱 / 筑梦岛）→ **不可能**：没有导出接口（没查到）。

整体判「中等」，是因为真正卡住的不是格式，而是语义：一条聊天记录要变成一次「自我验证」或一条「判断」，需要谁说的、什么时候、算不算数这三件事，而这三件事只有原文里才有——所以能迁的是经历，迁不了的是别人替她算好的结论。
