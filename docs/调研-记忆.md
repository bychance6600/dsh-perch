# 调研：给 dsh-roost 的长期记忆

> 2026-11。下面每个 GitHub 链接都打开过 README（HTTP 200），论文链接打开过摘要。项目约束：零依赖 Node 22、`events.jsonl` 只追加、derive 全量重放（现 2500 条、十几毫秒）。

## 一、结论先行

1. **三因子检索（Generative Agents）**：把 `searchEvents` 的 `includes` 计分换成 recency、importance、relevance 归一化相加；importance 用 solid/mentions/verified 代理，relevance 用现成的字符二元组 Dice，改 `lib/recall.js` 约 80 行，零依赖。
2. **失效不删除（Graphiti）**：`revise` 时给旧 belief 补 `supersededBy`、新 belief 补 `supersedes`，只加派生字段、不改正文，改 `lib/derive.js` 约 20 行，解决「改口后新旧判断并列、看不出谁盖谁」。
3. **记忆链接（A-MEM 的最小版）**：固化后给每条 belief 存 top-3 相似判断的 id，召回命中后做 1 跳扩散（权重 0.5），改 `derive.js` + `recall.js` 约 90 行，解决「说法不同但相关」只靠字面撞不上。

**零依赖有没有语义方案：没有真语义，有可用的近似。** `Intl.Segmenter` 分词 + 中文二字组 + 60 对人工同义词 + 自写 BM25（约 200 行，新文件 `lib/search-index.js`），能把「不开心」映射到「难过」这一类已知同义，不能处理开放域转述。真语义只能接 embedding，违反零依赖。

## 二、逐条方案

### 1. Stanford Generative Agents / ai-town（三因子检索）

**仓库**：[generative_agents](https://github.com/joonspk-research/generative_agents)、[ai-town](https://github.com/a16z-infra/ai-town)；论文 [2304.03442](https://arxiv.org/abs/2304.03442)。

**机制**：记忆流只追加；检索分 = recency + importance + relevance，三项各自归一化后等权相加。recency 按距上次访问的小时数每小时 ×0.995；importance 由 LLM 打 1–10；relevance 用 embedding 余弦。被召回会刷新 last access；累计重要性过阈值触发 reflection，反思写回记忆流。ai-town 是 TypeScript 重写，`convex/agent/memory.ts` 用 0.99^floor(hours)、先取 10 倍候选再重排，但依赖 Convex + OpenAI。

**适配**：`lib/recall.js` L124-178。importance 用 `solid ? 8 : min(8, 2 + mentions + verified)`；relevance 用现成 `dice(bigrams(query), bigrams(text))`；recency 用 `0.995 ** ageHours`；候选集内 min-max 后加 `min(3, refs)`。删掉 L150-157 的 `t.length` 加分。约 80 行，零依赖。

**风险**：recency 会压掉老疤，scarred 固定 +2；弱相关也会得分，`score == 0` 直接丢弃。

### 2. MemGPT / Letta（分层与换页）

**仓库**：[letta](https://github.com/letta-ai/letta)；文档 [context-hierarchy](https://docs.letta.com/v1-sdk/memory/context-hierarchy.md)；论文 [2310.08560](https://arxiv.org/abs/2310.08560)。

**机制**：主上下文 = 系统指令 + working context + FIFO 消息队列。memory blocks 在上下文内、agent 可 self-edit（rethink/replace/insert），建议 <50k 字符、<20 块；接近窗口上限触发 memory pressure，按 FIFO 驱逐并递归摘要写入 recall storage，原消息仍可搜；archival memory 在上下文外，靠 `archival_memory_insert/search` 按需取。本质是虚拟上下文分页，不是新存储引擎。

**适配**：roost 已是「8 条 solid + 身份/叙事 + 全量事件可搜」的小号三层，缺硬上限。在 `lib/derive.js` L771 取完 solid 后加 `solidChars` 上限（如 12000），超了按排名截断；约 20 行。不要引入 archival 向量层。

**风险**：分页解决上下文窗口，不解决召回质量；2500 条全量重放 15ms，分层只会多一处不一致。

### 3. mem0（只加不改）

**仓库**：[mem0](https://github.com/mem0ai/mem0)。

**机制**：2026-04 起改成 single-pass ADD-only：一次 LLM 调用抽事实，只 ADD，不 UPDATE/DELETE，记忆累积不覆盖；旧版是 LLM 判 ADD/UPDATE/DELETE/NOOP。检索用 semantic + BM25 + entity 多信号。需 LLM + embedding。

**适配**：这条是验证不是移植。roost 的 `revise` 已是追加新判断 + 旧判断标 refuted/refined，与新方向一致；可借的 entity 信号，`matchPeople` L217-230 已经在做。不增字段、0 行代码，把「不覆盖」写进 `docs/定过的取舍.md` 即可。

**风险**：别让模型自动抽 belief——`docs/定过的取舍.md` L17 是「她说话才算成长」，LLM 抽取会造出她没说过的话。

### 4. Zep / Graphiti（时间有效性）

**仓库**：[graphiti](https://github.com/getzep/graphiti)；论文 [2501.13956](https://arxiv.org/abs/2501.13956)。

**机制**：temporal context graph，实体/关系/事实带 validity window；事实变化时旧事实 invalidated 而非 deleted，能查「现在为真」或「某时刻为真」；episode 保留原始来源，每条派生事实可溯源；检索是 semantic + BM25 + graph traversal。需 Neo4j/FalkorDB/Neptune + OpenAI。

**适配**：`lib/derive.js` L462-466 现在只改旧 belief 的 status，没有反向指针。加 `supersededBy`（旧→新）、`supersedes`（新→旧）、派生 `validFrom/validTo`；不改事件流、不 bump schema（都是派生字段）。约 20 行。查「某时刻为真」直接截断 events 重放，store 已支持。不要引入图数据库。

**风险**：双时间（事件时间 vs 写入时间）在单机 2500 条没有收益；`supersededBy` 只在派生层，`memory-page.js` 要同步展示，否则看不出来。

### 5. A-MEM（Zettelkasten 链接）

**仓库**：[A-mem](https://github.com/agiresearch/A-mem)；论文 [2502.12110](https://arxiv.org/abs/2502.12110)。

**机制**：每条新记忆生成 note（content/tags/category/context/keywords/timestamp），用向量找历史相似记忆建链接；新记忆还能反向更新旧记忆的 context/tags（memory evolution）。依赖 ChromaDB + embedding + LLM。

**适配**：只抄链接，不抄 evolution。`derive.js` 建完 beliefs 后，对每条算与其它 belief 的 Dice，取 top-3 且 ≥0.35 存 `links:[id]`；`recall.js` 命中后把 links 里的判断以 0.5 权重加入结果并标「相关」。约 90 行，零依赖、确定性。不要改旧判断正文，那会破坏只追加。

**风险**：Dice 会把「今天很累」和「今天很忙」连一起；要求共享至少一个非停用二字组，links 最多 3 条；每次 derive 重算，别写回事件。

### 6. HippoRAG（海马体索引）

**仓库**：[HippoRAG](https://github.com/OSU-NLP-Group/HippoRAG)。

**机制**：OpenIE 抽实体/三元组建图，查询时从查询实体出发做 Personalized PageRank 多跳扩散；HippoRAG 2 增加 passage/entity/fact 多节点。需 GPU/embedding/LLM。

**适配**：不抄。roost 没有 NER，也没有图存储；硬做要 300+ 行且没有评测集。多跳召回用第 5 条的链接就够，PPR 是规模化后的优化。

**风险**：OpenIE 的实体质量决定一切，零依赖做不到。

### 7. MemoryBank + sleep-time compute（遗忘与巩固）

**仓库**：[MemoryBank](https://github.com/zhongwanjun/MemoryBank-SiliconFriend)、[sleep-time-compute](https://github.com/letta-ai/sleep-time-compute)；论文 [2504.13171](https://arxiv.org/abs/2504.13171)。

**机制**：MemoryBank 按 Ebbinghaus 曲线做记忆强度——时间衰减、被召回则强化，另有用户画像总结；实现要 A100 + ChatGLM + LoRA。sleep-time compute 是离线预计算上下文，降低在线成本，不是专门的巩固算法。

**适配**：`lib/derive.js` L755-760 现在是二值 `faded`（90 天）。要连续强度就加 `strength = exp(-ageDays/90) * (1 + mentions + 2*verified)`，只用于排序、不改 solid 判定，约 35 行。巩固做成聚类：Dice ≥0.8 的 belief 只留最早一条进 solid，其余标 `mergedInto`，约 60 行。sleep-time 不适用，derive 已经 15ms。

**风险**：连续强度会让「90 天退档」变模糊；合并会掩盖改口，必须保留 `mergedInto` 追溯。

### 8. 覆盖式重构 vs 追溯式（心理学）

**依据**：Bartlett 1932《Remembering》的「War of the Ghosts」；Nader, Schafe & LeDoux 2000（Nature 406:722-726，DOI 10.1038/35021052）。

**机制**：Bartlett 证明回忆是图式驱动的重构，细节会被补全/改写；Nader 等发现提取后记忆进入不稳定期，需再巩固才能稳定，期间可被修改。工程上没有把「再巩固」做成写入通道的仓库；最接近的是 A-MEM 改旧 note 的 metadata（不改正文）与 Graphiti 的 invalidate-not-delete，mem0 旧版的 UPDATE/DELETE 才是覆盖式。

**适配**：roost 的 `revise` 已是追溯式，方向对。补「说法链」视图：`lib/memory-page.js` 把 `supersededBy` 串成「原话 → 改口 → 现话」，约 30 行。事件流里的旧 text 永不重写。

**风险**：无；唯一要守的是旧正文不改。

### 9. 线索式召回（按人/事/时）

**依据**：Tulving & Thomson 1973 的 encoding specificity；ACT-R 激活 = base-level + 关联强度 + 噪声。工程上 Graphiti 按实体/边遍历、HippoRAG 按实体 PPR、A-MEM 按链接扩散，没有通用库把「人/事/时」做成标准槽。

**适配**：`lib/recall.js` L242-290 的 `registerRecall` 现在只收 query/days/kind/brief。加 `person`、`from`、`to`、`about` 四个可选参数，`searchEvents` 里按 `ev.person`、`ts` 过滤；schema 已有 person（`lib/schema.js` L322-336），但只由渠道层写，她自己的 utterance 没有 person，所以人物过滤只命中 heard；要覆盖她的话，用 `sessionId` 找同 session 的 heard 再传递，约 20 行。总共约 60 行。

**风险**：她的话没有 person 是结构性缺口，别假装能按人取全部；过滤为空要退回词面检索，否则「翻了没翻到」。

### 10. 零依赖近似语义检索

**仓库**：[MiniSearch](https://github.com/lucaong/minisearch)、[wink-bm25-text-search](https://github.com/winkjs/wink-bm25-text-search)。

**机制**：MiniSearch 零依赖、内存全文，支持 prefix/fuzzy/field boost/filter/自定义 tokenize，但排序只称「modern ranking」，不是 BM25；wink-bm25 是真 BM25（k1=1.2, b=0.75, k=1），但带 4 个依赖（wink-nlp 等），违反零依赖。Node 22 自带 `Intl.Segmenter`（ICU）可做中文词切分；本机 bash 没有 node，未实跑，标注「未在本机验证」。

**适配**：新写 `lib/search-index.js`（约 200 行）：`Intl.Segmenter('zh', {granularity:'word'})` 切词 + 中文二字组兜底；BM25（k1=1.2, b=0.75）；60 对同义词（难过/不开心/难受、开心/高兴、生气/愤怒、害怕/恐惧、累/疲惫…）；字段权重 text=1、person=2；缓存键 `${events.length}:${lastId}`，和 `solidIdsOf` 同一套。`recall.js` 只换 `tokensOf` 与计分，约 30 行。

**风险**：同义词表是人工的，覆盖有限；`Intl.Segmenter` 对网络新词会切碎，靠二字组兜底；上线前拿 30 条真实 query 做 before/after，别只看一例。

## 三、明确排除

- **Graphiti / Zep**：要 Neo4j/FalkorDB/Neptune + OpenAI，Python 服务；2500 条用图数据库是杀鸡用牛刀。只借「失效不删除」。
- **HippoRAG / HippoRAG 2**：GPU + embedding + LLM OpenIE，零依赖不可能。
- **A-MEM 原版**：ChromaDB + embedding + LLM；只借链接思想。
- **MemoryBank**：A100 + ChatGLM + LoRA，规模完全不匹配。
- **Letta 服务端**：Docker/Postgres，旧版在 archive 分支；roost 不需要多租户 agent server。
- **mem0 / ai-town**：都要 LLM/embedding API，ai-town 还要 Convex。
- **wink-bm25-text-search**：4 个运行时依赖，装完不能即用。
- **node:sqlite**：Node 22.5 才引入的实验特性，Electron 内置 Node 不保证暴露，FTS5 也不保证编译进去；不作为主路径。
- **远程 embedding**：违反零依赖、离线不可用、有成本；本地模型要原生模块/GPU。都不行。

## 四、三档建议

### 便宜（<200 行）

1. `lib/recall.js`：加 `person/from/to` 参数 + 同义词表 + 三因子重排，约 120 行。解决：搜「不开心」找不到「难过」；搜「上次和阿泽」不能按人过滤；solid 判断无论相不相关都压过新事。
2. `lib/derive.js`：`supersededBy/supersedes`，约 20 行。解决：她改口后，旧判断和新判断在列表里并列，看不出谁盖了谁。

合计约 140 行，不动 schema，不动账本。

### 中等（200–600 行）

1. 新建 `lib/search-index.js`：分词 + BM25 + 同义词 + 缓存，约 200 行；`recall.js` 接入约 40 行。解决长文本里关键词被短文本压过、8 条结果里同义改写召不回。
2. `lib/derive.js`：belief 链接 top-3 + 可选连续 `strength`，约 90 行；`recall.js` 1 跳扩散约 30 行。解决「相关但说法不同」的判断召不回。
3. `lib/memory-page.js`：展示 `supersededBy` 链和 links，约 80 行。解决记忆图谱里看不出改口链。

合计约 440 行，仍在派生层，不改事件格式。

### 大改（需要重新设计账本）

给事件加 `entities`、`topics`、全来源的 `person`、`validFrom/validTo`，做实体图 + PPR 或可选 embedding sidecar。要 bump `EVENT_SCHEMA_VERSION`、写迁移、重放全部 2500 条，约 800–1500 行。能解决开放域转述和跨人物关联，但本地 embedding 不是零依赖，远程又违反约束；现在不做。只有将来账本本来就要重设计时，才把 `entities` 一起加进去。
