# 调研：记忆图谱的三种画法

> 2026-11-12。只调研，不改代码。当前数据按任务口径：约 852 条判断；P1 之后有改口链；按人记；现有页面是 `lib/memory-page.js` 的 2D canvas 伪 3D 散点。

## 一、结论先行

**建议选「时间轴 + 聚类」作为 P6 的主视图，不选力导向 3D，邻接矩阵最多留作次要诊断视图。**

理由不是它最漂亮，而是它最直接回答她现在最需要回答的问题：**哪些判断是什么时候长出来的、哪一条改掉了哪一条、哪些话是同一个人说的。** 852 个点不需要第三个空间维度；需要的是把时间、改口链和人的线索画清楚。

**现在不改。** P6 在 `docs/v0.2-排期.md` 里排最后；P1 的改口链、P4 的按人参数、P5 的链接字段还没定完。图谱是这些字段的消费者，先画等于按临时口径写一遍，后面还要返工。

## 二、她现在的数据适合什么

| 数据 | 现在有什么 | 图上该怎么用 |
|---|---|---|
| 判断 | 约 852 条，正文、状态、时间、出处 | 点；点的大小只表示「被提到/被验证」的粗粒度，不做评分 |
| 改口链 | `revise` 事件、旧判断 → 新判断 | 有向边；只画被选中的链，不把几百条边一起铺满 |
| 按人 | 听过的话带 person，印象按人一条 | 分组或过滤；同一人的点靠近，但不把「人」画成人格标签 |
| 时间 | 每条有发生时间 | 横轴；这是现有散点最缺的一维 |
| 状态 | confirmed / refuted / refined | 颜色或边框；改口链两端要能看出方向 |

关键判断：**852 个点本身不贵，贵的是边和标签。** 任何方案只要把「所有边 + 所有标签」同时画出来，在 1400×900 和手机上都会糊。设计目标不是「一张图看全部」，而是「一张图回答一个问题，其余靠筛选」。

## 三、三种方案

| 方案 | 最适合 | WebView 渲染成本 | 手机 | 新依赖 |
|---|---|---|---|---|
| 力导向 3D | 找团、看全局聚集 | 高：3D 投影 + 每帧布局；手写 Barnes-Hut 才不 O(n²) | 差：遮挡、拖动与滚动打架 | 手写投影可零依赖；现成 three/d3-force-3d 则违反零依赖 |
| 时间轴 + 聚类 | 看生长、改口、按人 | 低：2D canvas，和现有页面同量级 | 较好：横轴可缩放/平移，标签可抽稀 | 零 |
| 邻接矩阵 | 看稠密关系、找块 | 中：画格子便宜，难在排序和交互 | 差：852 行在手机上不可读 | 零，但排序/聚类要自己写 |

### 1. 力导向 3D

**适合她的地方**：如果问题是「哪些判断自然聚成一团、团与团之间有没有桥」，3D 力导向最直观；旋转起来也最容易做出「记忆星云」的观感。

**不适合的地方**：

- 852 个点加边，3D 里前后遮挡严重；用户看到的是「一坨」，不是「哪条连着哪条」。
- 每帧跑斥力/弹簧是热路径；不引库就得自己写四叉树/八叉树近似，代码量和调参都不小。
- WebView 的 WebGL 可用，但不同宿主 GPU/驱动差异大；canvas 2D 做 3D 投影能跑，但点的排序、透明度和文字标签会迅速变贵。
- 手机上拖动旋转和页面滚动冲突；小屏上标签基本放不下。
- 真要做「力导向」，2D 已经够表达团；第三个维度没有多回答一个问题。

**结论**：不作为 P6 主视图。除非以后明确要「只看全局团块」的展示模式，否则不引入。

### 2. 时间轴 + 聚类

**适合她的地方**：

- 横轴就是时间，直接看出「第 1 阶段到第 4 阶段」的判断密度变化。
- 改口链天然是「左边旧判断 → 右边新判断」的有向连线；点中一条才展开它的链，不选中时只画淡色短线。
- 按人聚类可以做成纵轴分组或颜色分组；她听过谁的话、和谁有关，能在同一张图里过滤。
- 「今天页」并进来时，今天就是时间轴最右端的一段，不需要另造一套坐标。

**成本**：

- 复用现有 2D canvas 的缩放、平移、hover、筛选；新增的是时间坐标和分组布局，不是整套渲染器。
- 852 个点 + 少量边，桌面 WebView 没有压力；手机端可以只画点、标签按缩放级别抽稀。
- 零依赖；不需要物理模拟，布局是确定性的，刷新后不会「点自己跑掉」。
- 缺点是「团」的形状不如力导向自然；但可以用分组间距和淡色边界补，不追求有机感。

**结论**：主视图首选。

### 3. 邻接矩阵

**适合她的地方**：如果问题是「哪些判断彼此最密、哪些人/组之间连接最多」，矩阵比散点清楚；它能同时容纳很多边而不糊。

**不适合的地方**：

- 852×852 是 72 万格；全画出来在手机上就是一块噪点，在桌面上也要靠排序才有意义。
- 矩阵回答「关系密度」，不回答「她什么时候改的口」；和 P1/P4 的核心问题错位。
- 行/列排序本身就是一个聚类问题；排序不好，矩阵比散点更难读。
- 单个点的正文、时间、人物线索都要靠 hover/侧栏补，交互成本不比时间轴低。

**结论**：不做主视图。以后若要做「关系体检」可以当第二个只读视图，但不要和主图谱挤在一个入口。

## 四、如果 P6 真开工，建议的顺序

1. **先定问题**：一张图只回答一个主问题——「她什么时候改了口」；按人、按状态都做成筛选，不另开四张图。
2. **先做时间轴 + 分组**：横轴时间，纵轴按人/主题分组；先只画点和淡色组界，不画全量边。
3. **再加改口链**：选中一条判断才高亮它的 `supersedes` / `supersededBy`，默认不铺满。
4. **最后并入口**：按排期把「今天 / 图谱 / 印象」并成一个页面；今天页仍只读。
5. **手机验收**：390px 宽下能横滑、能点中一个点、能关掉标签；做不到就退回列表视图，不硬画。

## 五、为什么现在不改

- P6 在排期里是最后一项；P1 的改口链、P4 的按人、P5 的链接都还没收完。图谱要读这些字段，先做会按旧口径返工。
- 现有 2D 伪 3D 页面还能用：能缩放、能筛选、能点开一条看正文；它不是阻塞项。
- 真正要先定的是**图谱的验收问题**，不是渲染技术。问题没定，换 3D 也只是换一种糊法。
- 改图谱前先守住现有约定：`stats.hard` 现在是 tension 数，加连线统计别撞名（`docs/v0.2-排期.md` 第三节）。

## 六、没定的事

- 聚类按人还是按主题：P4 的 `person` 参数落地后才好定；现在按人会把「同一个人说的不同主题」硬拉在一起。
- 改口链默认画不画：建议默认只画选中链，但要看 852 条里实际有多少条 `revise`。
- 「今天页」并进来后，侧栏一项怎么分三处：这是 P6 的入口设计，不在本次调研范围。
